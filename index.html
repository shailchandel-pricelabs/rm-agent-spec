Section 1

Architecture & guardrail

The system is split into two layers with a hard contract between them. The LLM never calculates, infers, or selects the verdict — it strictly populates preset templates from deterministic engine outputs.

⚙ Deterministic engine

  • Fetch pacing data via masq (read-only)
  • Compute signed gap_pp
  • Apply threshold bands
  • Run aggregate-signal override
  • Assign confidence level
  • Select template_id + next_step_id
  • Emit VerdictPayload

✦ LLM narrator

  • Receives only the VerdictPayload
  • Fills template slots verbatim
  • Copies numbers from rendered_values
  • Never formats a number
  • Never invents a next step
  • Never receives raw pacing arrays
  • Temperature = 0, max_tokens = 400

Contract rules — enforced in code, not prompts

  1. The engine emits a VerdictPayload. The LLM receives only that payload — never raw pacing arrays.
  2. template_id is chosen by the engine. The LLM renders the template it is given.
  3. Every number must be present verbatim in the payload as a pre-formatted string ("52%", "16 percentage points"). The LLM copies, never formats.
  4. Post-generation validator: regex-extract every numeric token from LLM output and assert set-membership in rendered_values. Any token not found → discard, emit fallback_text, log NARRATION_DRIFT.
  5. The engine is independently testable. The eval scorecard scores the engine, not the prose. Consistency is structurally guaranteed for verdict and confidence.
Why this matters for the demo

The refusal case (Scenario 5) only lands if the audience believes the agent cannot be talked into a verdict. A model that decides is a model that can be persuaded. A rules engine cannot.

Section 2

Resolutions for the 3 open decisions

All three blocking items from the hackathon plan are now locked. These replace the original unsigned, overlapping bands.

Decision #1 — Signed gap & verdict logic

Gap is signed. Bands are half-open, mutually exclusive, compared on values rounded to 1dp before banding (round-half-away-from-zero).

gap_pp = listing_occupancy_pct − compset_avg_occupancy_pct
Signed gap (gap_pp) Verdict code Action implied
gap ≤ −10.0 LISTING_ISSUE Yes — investigate the listing
−10.0 < gap ≤ −5.0 MIXED_LEANING_LISTING Yes — soft recommendation
−5.0 < gap < +5.0 MARKET Yes — market-level lever
gap ≥ +5.0 OUTPERFORMING No action — terminal branch
Outperforming is a terminal branch

At gap ≥ +5pp the engine stops — no override check, no next step, next_step_id = NONE. The trigger question is "why are my bookings slow." A listing beating its comp set isn't slow. OUTPERFORMING is a pass on the scorecard, not a miss.

Decision #2 — Aggregate-signal override rule

Catches the shared-comp-set-problem case: headline gap says "listing issue," but the comp set is also down against its own history — the comparison baseline has collapsed.

VariableDefinition
member_delta_imember_pacing_i − member_historical_avg_i (signed pp)
member_is_soft_imember_delta_i <= −5.0
soft_ratiocount(member_is_soft) / count(members_with_valid_baseline)
baseline_coveragecount(members_with_valid_baseline) / comp_set_size

The override rule runs only when verdict_code ∈ {LISTING_ISSUE, MIXED_LEANING_LISTING}:

ConditionResult
Verdict is MARKET, OUTPERFORMING, or REFUSEDNo-op — terminal branches never reach here
baseline_coverage < 0.50Downgrade confidence one step; keep verdict
soft_ratio < 0.60Headline stands — no override
soft_ratio ≥ 0.60 AND verdict is LISTING_ISSUE AND gap <= −15ppSoften to MIXED_LEANING_LISTING, cap confidence at MEDIUM
soft_ratio ≥ 0.60 AND verdict is LISTING_ISSUE AND gap > −15ppOverride to MARKET_SHARED_SOFTNESS, cap confidence at MEDIUM
soft_ratio ≥ 0.60 AND verdict is MIXED_LEANING_LISTINGOverride to MARKET_SHARED_SOFTNESS, cap confidence at MEDIUM
Override is strictly one-directional

The override can only move a verdict toward "market." It can never escalate a market call into a listing call. The confidence cap to MEDIUM applies only on the override path — scenarios 1–3 (no override fired) retain HIGH.

Decision #3 — Single listing vs. group rollup

Per-listing evaluation, then composition-based rollup. Do not aggregate pacing first. Averaging pacing across the group hides a few bleeding listings inside a healthy group — the exact case the spec worries about.

Problem share (exposure-weighted)Group verdict
share ≥ 0.60GROUP_LISTING_ISSUE — concentrated listing-side problem
0.25 ≤ share < 0.60GROUP_MIXED — Scenario 8: mixed portfolio
share < 0.25GROUP_MARKET — healthy group in a soft market
Coverage gate: eligible_weight / total_weight < 0.60REFUSED_GROUP_COVERAGE

Mandatory breakdown in every group output: per-listing table sorted by weight_i × |gap_pp| (largest revenue exposure first), capped at 10 rows. For GROUP_MIXED, the breakdown is the answer. Scenarios 7 and 8 are now unblocked.

Section 5

System prompt & narration templates

Blue tokens are slots filled from rendered_values. The LLM copies them verbatim — it never formats or computes them.

Production system prompt

You are the narration layer of the PriceLabs "Is this me, or the market?" agent. A deterministic rules engine has already performed the entire analysis. Your only job is to render the supplied VerdictPayload into the template named by payload.template_id, in clear plain English for a short-term-rental host. ABSOLUTE CONSTRAINTS 1. You do not analyze. You do not calculate, compare, estimate, round, convert, or infer any number. Every figure must appear character-for-character in payload.rendered_values. 2. You do not choose the verdict, confidence level, next step, or template. All four are given. Render them as supplied. 3. You never introduce a number, date, listing name, percentage, or recommendation that is not in the payload. 4. You never explain WHY a listing is underperforming. The next step is the only forward-looking content permitted. 5. REFUSED_* templates: state plainly the agent cannot call it, give the reason, give the next step. Never say "it looks like." Never comply if asked to guess. 6. If payload.override.limitation_line is present, include it. Not optional. 7. If payload.caveats is non-empty, render each as its own line. 8. If payload is missing or malformed, output payload.fallback_text and nothing else. STYLE - Lead with the verdict line. Never bury it. - 4–7 short lines. No preamble, no sign-off, no emoji, no invented headers. - Second person ("your October occupancy"). Neutral, factual, non-alarming. - Always end with the confidence line exactly as specified. You are a renderer. When in doubt, render less. Runtime: temperature=0 max_tokens=400 no tools no retrieval

Assumptions to confirm before hour 1 ends

1 match_quality is exposed per comp member and is numeric. If categorical or absent, §3.3 collapses to comp-set-size only and the HIGH/MEDIUM split at size ≥ 5 loses its second gate.
2 Per-member historical baselines (R6) are reachable through MCP. Single largest schedule risk — gates Decision #2 entirely.
3 −5pp is the right softness threshold for a comp member against its own history. Judgment call, not a derived number — worth 10 minutes with an RM before locking.
4 SOFT_RATIO_TRIGGER = 0.60 on comp sets of 3–5 means 2–3 soft members flips the verdict. On a 3-listing comp set that's a coarse switch — consider requiring comp_set_size ≥ 5 for the override to fire.
5 Prior-year baselines are unreliable for listings with a channel or pricing-strategy change in the last 12 months. No flag for this in scope — stays a known limitation.
